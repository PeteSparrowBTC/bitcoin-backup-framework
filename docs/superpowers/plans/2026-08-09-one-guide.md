# Plan: one guide, three repositories, and a site at guide.petesparrow.com

Date: 2026-08-09

This plan decides where the writing lives, now that there is enough of it to trip over, and
what has to happen before a video series can point at any of it.

Nothing here changes what any document says. It changes what is in which repository, and in
what order to do that, so the moving does not lose history or break links.

## 1. The problem

There are two prose repositories and neither is complete on its own.

- **`bitcoin-backup-framework`** opens at "is the secret worth protecting?" It assumes the
  reader already holds a seed.
- **`seed-generation`** is how the reader got one. It is 28,790 words across eleven documents,
  plus printables.

A reader who follows one needs the other, and there is nothing in either that says so. For a
series billed as start to finish, that seam has to be explained in every episode that crosses
it, which is most of them.

## 2. The shape

Three things, not two, and the criterion is not the file format.

| | contains | why |
| --- | --- | --- |
| `petesparrow.com` | the front door: what the service is, and the offer | 184 lines, hand-written, changes twice a year |
| **the guide** | framework, generation, drills, every word of prose | one reader, one sitting, one order |
| the tools | `dice-to-seed`, `slip39-backup`, `AgeSharp`, `tails-appimage` | each is audited on its own before it is trusted |

**Prose merges. Tools do not.** The test is not "is it documentation", it is *does one person
read both in sequence*. The framework and the generation docs pass that test. The tools do not:
nobody reads a converter and a splitter in order, they audit whichever one they are about to
run.

### Why the tools stay out

`dice-to-seed`'s whole claim is that it is small enough to read before you trust it with a key,
and its rules say to treat every change as a change to key-generation code. That rule is only
credible while the repository contains key-generation code and little else. Move it into a
repository holding 30,000 words of prose, a printables folder and two other tools, and a
reviewer's first job becomes working out which four hundred lines matter. Nothing about the
code changed; the claim got weaker anyway.

Two mechanical costs of merging tools, for completeness:

- **Tags stop meaning anything.** `dice-to-seed` is at `v1.0.0`. In a combined repository,
  `v1.0.0` of what? Prefixed tags and conditional release workflows, for no reader benefit.
- **Branch protection gets diluted.** `dice-to-seed` requires a pull request per change
  because it makes keys. Merge prose in and either every typo goes through that ceremony, or
  the rule is relaxed and stops meaning anything.

### What the split costs, honestly

Discovery and link rot. A reader landing on one repository has no idea the others exist, and
today none of them link to each other. That is a header in each README, not a reason to
restructure.

## 3. Order of work

Written as an order because one of these is a live error and the rest are improvements to
things that already work.

### Step 0: correct the Krux error in `seed-generation`

**Do this first and on its own.** It is the only thing currently wrong for a reader, and
merging a wrong fact relocates it while making the history harder to read.

`docs/dice.md` and `docs/methods.md` state that Krux hashes the d6 roll string dash-separated.
It does not. From `src/krux/pages/new_mnemonic/dice_rolls.py`, unchanged in every tag back to
v22.08.2:

```python
"".join(self.rolls) if self.num_sides < 10 else "-".join(self.rolls)
```

The dash is the **d20** convention, needed because a d20 face value can be two digits and `1`
then `2` would otherwise be indistinguishable from `12`. With six faces that cannot happen, so
Krux joins with nothing, exactly as Coldcard and SeedSigner do. There is no d6 dialect split.

A reader following the current text would hash the wrong string, get different words, and
conclude their device was broken. That is precisely the false alarm the repository exists to
prevent, which makes it the most expensive kind of error it could contain.

`dice-to-seed` corrected this and `seed-generation` did not, because the same fact was written
down in two places. That is the argument for one canonical home per fact, and it is the reason
for the rest of this plan.

### Step 1: write the missing chapters while they are still small

Easier to write into a repository than into a merge. Each is absent today:

| chapter | why it matters |
| --- | --- |
| **Test spend** | Not mentioned anywhere. Send a small amount in, then spend it out, before trusting the setup. Receiving proves nothing; spending proves the whole path |
| **Recovery rehearsal** | Mentioned twice, never as a procedure. Wipe a spare device, restore, confirm the same first address. The most skipped step in self-custody |
| **Verifying the device itself** | Sealed packaging, firmware signatures, reproducible builds. "How do I know this hardware is what it claims" is unanswered |
| **The defect playbook** | `incident-2026-coldcard.md` is history. Generalise it: a defect is announced, am I affected, how do I rotate a seed safely |
| **Watch-only and the non-secret backup** | Beyond default single-sig the seed alone does not restore you. Descriptors and labels need their own backup, and being non-secret they can live where the seed cannot |

The first two are also the best filming: they are procedures you can show, not concepts you
have to narrate.

### Step 2: merge the prose

`git subtree` so authorship survives. Twenty-eight thousand words of written argument arriving
as one "add docs" commit would destroy the record of when each claim was made and why.

```bash
git remote add seed-generation https://github.com/PeteSparrowBTC/seed-generation.git
git fetch seed-generation
git subtree add --prefix=docs/generating seed-generation main
```

Then fold the current `README.md` into the same `docs/` tree so the top level is a table of
contents rather than an 800-line document. It is already too long to link into precisely, which
matters when every video description points at one section.

**Keep the generation chapters in their own voice.** `seed-generation` is deliberately
vendor-neutral: it points at Coldcard, SeedSigner and Ian Coleman without preference. The
framework is opinionated and recommends tools the same author wrote. Merged carelessly, a
neutral reference quietly becomes a vendor pitch. Say so in the preamble of those chapters, and
do not let the recommendations bleed upward into them.

### Step 3: rename the repository

`bitcoin-backup-framework` describes about a third of what it would then be. GitHub redirects
on rename, so this is cheap and should happen once, before anything links to it in a video.

### Step 4: publish `guide.petesparrow.com`

GitHub Pages from the guide repository, one CNAME.

The landing page stays exactly as it is: hand-written, no build step, on the apex domain. It is
a different object with a different rhythm, and it should not be rebuilt every time a chapter
changes.

The guide gets a build. Its README says no build step and zero external requests; the second is
the promise to visitors and must survive, the first is a convenience for the author and does
not. Any static generator can be configured to emit no analytics, no web fonts, no JavaScript
and no external requests, which is the property that matters and is also the property the tools
already hold themselves to.

The reason for a subdomain rather than a path: independent deploys, and stable per-episode
URLs. `guide.petesparrow.com/generating/dice` is a link that can sit in a video description for
years.

### Step 5: leave the old paths working

`seed-generation` becomes a stub README pointing at the new home rather than being deleted. It
is public and may already be linked from elsewhere; a merge does not redirect deep links to
files the way a rename redirects a repository.

Then update the inbound links: `slip39-backup` and `dice-to-seed` both point at
`seed-generation` today, and `dice-to-seed` links two specific sections of `docs/dice.md`.

## 4. What each repository gets as a header

The discovery problem, solved cheaply. One block at the top of every README:

> Part of a set: **the guide** at guide.petesparrow.com, **dice-to-seed** for converting dice
> rolls to a seed phrase, **slip39-backup** for splitting one across backups.

## 5. Decisions left to the human

- **The new name.** `bitcoin-self-custody` says what it becomes; there may be a better one, and
  it should be chosen before a video points at it.
- **Whether `seed-generation` links to `dice-to-seed`.** That repository is deliberately a
  referee, pointing at other people's tools; linking to one by the same author changes it to a
  participant. It is more defensible now that `dice-to-seed` agrees with two vendors' published
  vectors, but it is still a deliberate choice rather than an obvious one.
- **The generator.** Whatever produces a static site with no external requests. Not a decision
  worth a long argument, and easy to change while the audience is small.
- **Whether inheritance stays out of scope.** The framework says so explicitly and gives its
  reasons. A start-to-finish series will be asked about it, and "deliberately not covered, here
  is why" is a fine answer as long as it is prepared rather than improvised.
